# v1.1 — Hooks plan

Status: planned release scope. This document defines work to design and validate;
the proposed API is not yet implemented.
Product version v1.1 is separate from the manifest and JSON envelope versions.
Their versions change only if their own compatibility contracts require it.

## Outcome

Projects express workspace behavior in short Lua scripts, generally 10–100 lines.
The scripts describe decisions; Go handles reliable interaction with the host.
The substrate should make copying configuration, installing dependencies, claiming
resources, and reading project metadata straightforward without embedding language
or application conventions in WTF.

Go owns identity resolution, file operations, subprocess execution, cancellation,
ownership records, authenticated provider interaction, and structured reporting.
Lua owns source selection, overwrite/merge policy, package-manager selection,
component ordering, port selection, and how values reach applications.

## Starting point

The current pilot already provides explicit TOML-selected registration, bounded
project-local imports, operation overrides, named hook composition, command
stages with input fingerprints and reuse checks, and repository-scoped claims.
It also has GitHub observations and a host-managed Linear review connection.
Those integrations are not yet a general Lua provider API.

The expanded filesystem/environment API, per-component execution directories, and
general provider reads below are planned additions. [hooks.md](hooks.md) remains
the current contract until implementation changes it.

## Proposed API surfaces

Names are design candidates. Namespace migration and compatibility with existing
`ctx:stage`, `ctx:hook`, and claim methods must be decided before implementation.

| Surface | Needed operations | Project decisions |
|---|---|---|
| Workspace context | Current identity; resolve an explicit source; inspect/list workspace records | Which workspace supplies inputs |
| `ctx.fs` | Exists/stat, read, write, copy, symlink, readlink, list, remove | Which files; copy versus link; destination policy |
| `ctx.env` | String names/values; read selected invocation variables; build child environment settings | Which values a command receives |
| Command execution | Run argv with cwd, env, timeout; optionally name and record the command | Which tool, arguments, order, and reuse check |
| `ctx.resources` (design pending) | Existing inspect, claim, release, port claim and listening operations | Claim semantics, candidate ports, retry and teardown policy |
| `ctx.github` | PR, check, and review reads through existing host integration | Which repository/PR/check data matters |
| `ctx.linear` | Issue/review reads through existing host connection | Which workspace/issue/review data matters |

### Commands and recorded steps

Command execution means running a project-selected tool, such as a dependency
installer, with explicit arguments and a working directory. A "stage" in the
current pilot is simply a named command with a recorded result, optionally with
inputs and a check that allow reuse. It is not a processor or a separate workflow
language. Lua still decides the sequence. The API should make a simple command
easy to run; recording and reuse are available when the recipe needs them.

### Environment settings

The proposed baseline is string variable names and string values in a settings
table, passed directly to the child process environment. Values are not assembled
into shell `export` commands or interpolated into command strings. Define whether
settings inherit the invocation environment, override values, or unset variables;
preserve value case and distinguish an empty string from an absent variable.

Strings are not inherently secret. Host-generated output and saved records omit
values; scripts receiving ordinary strings can still read and print them. Opaque
secret handles would be a separate API decision if a real recipe requires them.

### Shared conventions

- Paths identify their workspace explicitly. Current-workspace destinations and
  source-workspace reads are distinct; component cwd is a bounded relative path.
  Define symlink behavior and filesystem boundaries, including removal, before
  exposing the operations.
- Lua gets ordinary tables, strings, booleans, and iterable records. Define field
  names, array ordering, absent fields, pagination, and empty results consistently.
- Select one error convention for new APIs. Prefer typed raised errors with stable
  `code` and `message`, catchable through Lua's normal protected calls; document
  compatibility with existing methods that return an error code.
- Missing files, claim conflicts, missing provider records, unavailable providers,
  authentication failures, and cancellation remain distinguishable. Optional
  results must not turn remote failures into empty successful results.
- File `remove`, resource `release`, and workspace lifecycle removal have distinct
  effects. Recursive directory removal is explicit. Workspace removal continues
  through validated lifecycle delegation rather than a filesystem shortcut.
- Host records and diagnostics describe operations without storing credentials or
  environment/file contents. Keep sensitive values out of argv and document that
  project-controlled commands and logging can expose their own inputs.
- Long operations share cancellation and bounded timeouts. Provider pagination is
  explicit and bounded; no helper silently downloads every result.
- File operations expose outcomes such as copied, preserved, missing, or failed.
  Command stages retain completed/failed work. Hook return values and their CLI
  representation need an explicit contract rather than accidental raw table dumps.

### Resource claims remain a separate design topic

Retain the existing claims substrate while working out port and other claim
semantics from actual recipes. The resource namespace is provisional; expanded
claims are not a prerequisite for file, symlink, command, or provider-read work.
Application wiring remains in Lua regardless of the eventual claim API.

## Recipe 1: Copy or symlink workspace configuration

Story: create a workspace, copy or symlink selected environment files from a source,
and prepare commands with the values that this project requires.

Whole-file copying and symlinking are both first-class release requirements.
Lua supplies the file list and chooses copy or symlink explicitly. It decides
whether missing sources block preparation or are optional. Existing destinations
are preserved by default in the example; replacement is an explicit recipe choice.
Parsing variables is a separate operation.

A copy gives the workspace independent contents. A symlink keeps the destination
connected to its source and can link files or directories. The API must distinguish
the link itself from its resolved target. Removing a symlink removes the link,
never recursively removes its target; replacement must not write through a link
and modify the source. Define whether copying a symlink follows its target or
preserves the link, rather than silently selecting one behavior.

Go supplies source resolution, bounded reads, atomic destination writes/copies,
and outcome records. Lua may later combine a claimed port with a child environment
map. Reading invocation variables does not change the caller's shell environment.

Acceptance:

- Short Lua recipes copy files and create file/directory symlinks between explicit
  workspace identities. Symlinking is not deferred to a later release.
- Repeating preparation preserves destination edits under the example policy.
- Repeating an identical symlink request can report reuse; a different existing
  target follows explicit preserve/replace policy. Reading the link target and
  inspecting a broken link have documented behavior.
- Removing a symlink leaves the source intact, including when the source is a
  directory. Copying and replacing links follow the stated target policy.
- Missing optional and required files produce different documented outcomes.
- Failed copy/write leaves no partially written destination; diagnostics contain
  operation metadata, not configuration values.
- A separate example reads selected invocation variables and passes overrides to
  a command without persisting those values in host records.

Variable-level `.env` parsing/merging is an open decision, not required for the
whole-file recipe. Add it only if a concrete story requires its format semantics.

## Recipe 2: Prepare dependencies across languages

Story: prepare a Python backend and a JavaScript frontend in one workspace, using
project-selected tools and component directories.

Lua chooses the component list, commands, lockfile inputs, order, optional groups,
and output readiness checks. Go supplies cwd/env-aware stages and retained results.
The example uses the existing project environment and shared package-manager
caches. WTF does not install toolchains or choose a package manager in Go.

Acceptance:

- One short Lua recipe prepares both components in explicit directories.
- If the second install fails, the workspace and first completed stage remain
  available; retry can reuse the first stage only under its declared reuse policy.
- Changed lockfiles invalidate reuse. A live check detects deleted or unusable
  dependency outputs even when the previous command succeeded.
- Cancellation identifies the interrupted stage and permits a subsequent retry.
- Default execution is sequential; the recipe delegates installation semantics
  and cache/environment handling to each existing language tool.

## Recipe 3: Read GitHub and Linear

Story: a hook reads the workspace's associated GitHub PR and checks, and an explicit
Linear issue or linked review, then branches on ordinary Lua data.

Use a small set of common helpers over the existing host integrations.
The host owns connection selection and transport; Lua never acquires tokens.
Keep the existing GitHub authentication and Codex MCP OAuth Linear integration,
including verification of the intended Linear workspace. Host-managed interaction
does not require replacing the existing bridge with a new direct Go client.
No model turn is part of a provider read.

Start by exposing the PR/check/review reads WTF already performs and the Linear
reads needed by the recipe. Account selection, repository/workspace identifiers,
response normalization, pagination, freshness, and bounded retries are part of
the API contract. A general provider request gateway is optional future work,
not a requirement for these helpers.

Acceptance:

- A short Lua recipe reads PR/check and issue/review records and iterates over them.
- Wrong-workspace routing fails explicitly; absent or ambiguous association never
  guesses an identity from a workspace name.
- Missing, unassociated, and unavailable states remain distinct. Failed refresh
  preserves a marked prior observation when one exists.
- Existing repository/account cache boundaries are retained; transient failures
  are never cached as confirmed missing results.
- Requests have timeouts and page/result bounds. Hook decisions can inspect
  observation time, stale state, and whether a result set is complete.
- Fixtures cover the data/error contracts; live read evidence verifies connection
  routing separately. Tokens and child connection diagnostics are not exposed.

Remote mutations are outside this release scope.

## Delivery slices

1. **Contract design:** write the three proposed recipe sketches and API reference;
   agree path scopes, data/error conventions, method names, compatibility, and
   hook results. Review recipes before building the substrate.
2. **Local files and environment:** deliver the first recipe and focused checks for
   read/write/copy/symlink/removal semantics, string env settings, and retry preservation.
3. **Command execution:** support component cwd and env, with optional recording;
   deliver the multi-language recipe. Compose existing claims with child env only
   where the recipe needs them; expanded claim semantics remain separate work.
   Preserve identity validation and lifecycle delegation.
4. **Provider reads:** expose common reads over existing
   connections; deliver the metadata recipe and account/error/pagination checks.
5. **Dogfood and document:** exercise the recipes in real workspaces; publish the
   supported Lua reference, failure/repair examples, and release evidence.

Each slice records proposed versus implemented versus locally/live-verified
behavior. Run focused checks with one worker by default, one expensive validation
at a time. Existing CLI middleware still governs all added command surfaces:
case-insensitive names/flags, preserved opaque values and argv, inherited defaults,
useful help, and one versioned JSON stdout result with logs on stderr. Extend the
command-tree tests only when command surfaces change.

## Decisions to settle before implementation

- Namespaced APIs, retained flat methods, or additive namespaces with compatibility
  aliases; choose an API-version policy for project scripts.
- Source-workspace selection and allowed filesystem scopes; link target inspection,
  broken links, copy-through-link and recursive removal behavior; overwrite options.
- Environment inheritance, overrides, and unsetting using string settings.
- Typed error behavior, optional results, hook return values, and serialization.
- Which existing GitHub/Linear reads deserve helpers;
  how accounts, pagination, and freshness appear to Lua.
- Whether reusable recipes stay project-local initially or warrant bundled Lua
  modules. Start project-local; package loading/versioning follows real reuse.

The release does not require a workflow language, plugin marketplace, generic HTTP
SDK, daemon, durable process supervisor, cross-repository port leases, or native
language/Docker/database providers. Scripts continue to use project tools for
those policies. The release is complete when all three stories work through the
documented Lua substrate with the stated failure and reporting behavior.
